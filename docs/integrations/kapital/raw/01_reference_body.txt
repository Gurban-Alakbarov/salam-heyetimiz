## Payment Status
| Description | Status | Note |
| The payment is initially created with a PENDING status. In this case, no transaction is created, and the next action is waiting for the customer or client. | pending |
| The payment is considered successful when the merchant completes it. | succeeded |
| When no action is performed after the payment is created, it will be automatically cancelled after the expiry date provided by the merchant, or if the merchant intentionally wants to cancel the order. | canceled |
| This condition is utilized when the merchant intends to perform after compelation (only for cards) | waiting_for_capture |

## Payment Cancelation
Payment can be canceled by merchant, customer or payment network. Each party has its own cancelation reasons.
| Description | Party |
| Internal schedulers continuously monitor payments to finalize them. If a payment is eligible for cancellation, the system will cancel it as part of the checkout process.. | CHECKOUT |
| If merchant wants to cancel payment before customer pays it can use cancel API. In this case cancelation party will be merchant. | MERCHANT |
| M10, Birbank, or the bank can also cancel the payment. In such cases, the cancellation is initiated by the payment network. | PAYMENT_NETWORK |
| Description | Reason |
| When merchant cancels payment. | CANCELED_BY_MERCHANT |
| When payment network cancels payment. | CANCELED_BY_PAYMENT_NETWORK |
| When customer does not confirm payment in time. | EXPIRED_ON_CONFIRMATION |
| When customer does not have sufficient funds. | INSUFFICIENT_FUNDS |
| When 3DS verification is failed. | THREE_DS_VERIFICATION_FAILED |
| Such as when the capture is not performed in time. | EXPIRED_ON_CAPTURE |
| For card payments, if the issuer declines to process the payment, the transaction will fail and the customer will be shown a failure page. | ISSUER_DECLINE |
| Such declines are uncommon but can occur in extreme cases. | GENERAL_DECLINE |

## Webhook
image.png
To monitor the status of payments or refunds, you can set up event webhooks. Before processing webhooks merchant should provide webhook url. Merchant can register events listed below: 

### Available events
- payment_succeeded
- payment_canceled

### Payload
Webhook requests are sent using the POST method, and an HTTP 200 status is expected in response. If a different status or an error occurs, a retry mechanism is triggered, resending the data. Multiple retry attempts are made within an hour. If no successful (200) response is received after the predefined number of retries, the event is discarded.

```
{
  "event": "payment_succeeded",
  "payload": {
    "id": "e469456c-0a53-4c31-bb43-d77ab197f94a",
    "type": "purchase",
    "paymentMethod": "birbank",
    "status": "succeeded"
  }
}
```

### Signature
In order to verify payload we provide signature header.  The primary goal is to ensure that the payload received by the system:
- Has not been altered during transmission
- Comes from a trusted source that holds the same shared secret
- Is processed only if the integrity and authenticity of the data are verified
Each incoming request is included a cryptographic signature (X-Signature) header. Upon receipt, the system performs the following steps:

### Code Sample

```
public class HmacShaVerifier {

    private static final String HMAC_SHA_256 = "HmacSHA256";

    public boolean isValid(String payload, String signature, String sentSignature) {
        try {
            Mac mac = Mac.getInstance(HMAC_SHA_256);
            SecretKeySpec secretKeySpec =
                new SecretKeySpec(signature.getBytes(StandardCharsets.UTF_8), HMAC_SHA_256);
            mac.init(secretKeySpec);
            byte[] hash = mac.doFinal(payload.getBytes(StandardCharsets.UTF_8));
            String generatedSignature = Base64.getEncoder().encodeToString(hash);
            return generatedSignature.equals(sentSignature);
        } catch (Exception e) {
            throw new RuntimeException("HMAC verification failed", e);
        }
    }
}
```
